Why a host would offer this

A Wrapped is the one thing a Minecraft server posts in December that its players actually forward. Every one of those cards carries the server's name and icon, and the players who see it go looking for the server that made it. For you it is a feature nobody else in your market has, it costs you one scheduled task per server, and there is nothing to install into the game.

1 · Create

One POST when a customer switches it on. You get back their public URL and an upload key.

2 · Send stats

A scheduled task on the server runs our one-line shell client, or your panel posts the folder itself. Twice a year is enough.

3 · Hand it over

Show the customer their link and a claim URL, and they own the page from then on.

Quick start

Three calls, start to finish. Everything else on this page is detail.

# 1 · does my token work
curl https://wrapped.gg/v1/host/ping \
  -H "Authorization: Bearer wgg_host_yourtoken"

# 2 · create a Wrapped for one customer's server
curl -X POST https://wrapped.gg/v1/host/servers \
  -H "Authorization: Bearer wgg_host_yourtoken" \
  -H "Content-Type: application/json" \
  -d '{"name":"Bobs SMP","external_id":"ptero-1a2b3c"}'

# → { "slug": "bobs-smp-k7m2p",
#     "url": "https://wrapped.gg/bobs-smp-k7m2p",
#     "upload_key": "wgg_live_…",
#     "claim_url": "https://wrapped.gg/claim/…" }

# 3 · send the stats, from the game server's own folder
curl -sL https://wrapped.gg/u | sh -s -- --key wgg_live_…
That third line is the whole integration It finds the world itself, reads the stats folder, flattens a 61 MB folder into an 8 MB upload in the client, and never touches the running server - it is safe with players online. Needs curl and python3, both of which are already in every Pterodactyl egg.

Getting a partner token

Partner tokens are issued by hand, because we would like to know who is sending us other people's data. Message Tehlo on Discord with your company name, your panel software, and roughly how many servers you expect to enable it for. It is free, and there is no contract to sign.

Your token looks like wgg_host_ followed by 48 characters, and it:

  • authenticates every call under /v1/host and nothing else
  • is stored as a hash, so we cannot show it to you again - keep it in your panel's secret store, not in an egg variable a customer can read
  • can be rotated or revoked by asking, and takes effect immediately
Never put a partner token on a game server It can create and delete Wrapped pages for every customer you have. The per-server wgg_live_ upload key is the one that belongs on the machine - it can do exactly one thing, for exactly one server.

Where the stats folder lives

Minecraft writes one JSON file per player. Where it puts them changed recently, and if you are building your own uploader you need to handle both:

Minecraft versionPath
26.X and newer world/players/stats/<uuid>.json Per-player files moved under a players folder
25.X and older world/stats/<uuid>.json Still the path on most servers running today
Any usercache.json Server root, next to server.properties. Turns UUIDs into names.

world is whatever level-name in server.properties says it is, and the _nether and _the_end folders never contain stats. Our shell client resolves all of this itself - it checks world/players/stats first, falls back to world/stats, and searches from the server root if neither exists. If you write your own uploader, do the same in that order.

API reference

Base URL https://wrapped.gg. Everything is JSON, and every call carries Authorization: Bearer wgg_host_…. Errors come back as { "error": "code", "message": "..." } with a matching status.

GET/v1/host/ping Checks your token and reports how many servers you have created. 
{ "ok": true,
  "partner": { "name": "BlockHost", "slug": "blockhost" },
  "servers": 412,
  "max_servers": 10000 }
POST/v1/host/servers Creates a Wrapped. Idempotent on external_id, so it is safe to retry and safe to call from a button a customer can double-click.
FieldTypeMeaning
name required string, 2-48 The server's name, as the customer would write it. Shown on the page and on every share card.
external_id required string, 1-64 Your own id for the server - the Pterodactyl UUID, the Multicraft id, whatever you already have. This is the idempotency key, and it is how you can address the server later without storing anything of ours.
slug string, 2-24 The readable part of the URL. Defaults to the name. A random five-character suffix is always appended, so nobody finds a customer's page by guessing.
description string, ≤280 One line, used when the link unfurls in Discord.
published boolean Defaults to true. Pass false to build privately and publish later.
rotate_key boolean Only read when the external_id already exists. Issues a fresh upload key and revokes the previous panel key.
 
// 201 Created
{ "server_id": "01jd2…",
  "external_id": "ptero-1a2b3c",
  "name": "Bob's SMP",
  "slug": "bobs-smp-k7m2p",
  "url": "https://wrapped.gg/bobs-smp-k7m2p",
  "published": true,
  "claimed": false,
  "created": true,
  "upload_key": "wgg_live_…",          // shown once. store it.
  "claim_url": "https://wrapped.gg/claim/…",
  "claim_expires_at": 1801234567,
  "upload": {
    "endpoint": "https://wrapped.gg/v1/snapshots",
    "shell": "curl -sL https://wrapped.gg/u | sh -s -- --key wgg_live_…"
  } }

Call it again with the same external_id and you get 200 with "created": false and "upload_key": null - the existing Wrapped, unchanged, and no key churn for a cron that is already running. Add "rotate_key": true when you genuinely need a new one.

GET/v1/host/servers/:ref One server, plus how its last upload went. :ref is our server_id or ext:<your external_id>. 
curl "https://wrapped.gg/v1/host/servers/ext:ptero-1a2b3c" \
  -H "Authorization: Bearer wgg_host_yourtoken"

{ "server_id": "01jd2…", "slug": "bobs-smp-k7m2p",
  "published": true, "claimed": false,
  "players": 3244, "built_at": 1801230000,
  "last_snapshot": { "id": "01jd3…", "state": "ready", "error": null,
                     "players": 3244, "bytes": 8123456,
                     "received_at": 1801229800, "built_at": 1801230000 } }

state is queued, building, ready or failed. On failed, error is a sentence you can show a customer as-is.

GET/v1/host/servers?limit=50&before=<created_at> Everything you have created, newest first. Page with next_before until it comes back null.
PATCH/v1/host/servers/:ref name, description, published. Refused with 409 claimed once a customer has taken the server over.
POST/v1/host/servers/:ref/key Rotates the upload key. The previous panel key stops working immediately - this is what you call after a leak or a cancellation.
POST/v1/host/servers/:ref/claim A fresh single-use claim link, for the customer who lost the first one.
DELETE/v1/host/servers/:ref Removes the server and every upload, build and player page with it. Refused with 409 claimed once a customer owns it.

Sending the stats

Two ways, and they hit the same endpoint. Pick the shell client unless you have a reason not to - it is the one we test against every release. For how many times to run it, see how often to send.

The shell client recommended

curl -sL https://wrapped.gg/u | sh -s -- --key wgg_live_…

Run it from the folder holding server.properties. It reads level-name, finds the stats folder on either 26.X or older layouts, picks up usercache.json, flattens everything to gzipped NDJSON in one pass and posts it. POSIX sh: no bash, no jq, no node. It exits non-zero with a plain-English message on failure, so a panel can surface the reason without parsing anything.

Useful flags: --world /path to skip detection, --source your-panel to tag the upload as yours in our metrics, and --quiet for cron.

Posting it yourself

POST/v1/snapshots Authenticated with the server's wgg_live_ key, not your partner token. 
POST /v1/snapshots
Authorization: Bearer wgg_live_…
Content-Type: application/x-ndjson
Idempotency-Key: sha256 of the body - makes a retry free
X-Wrapped-Source: your-panel

# one line per player, gzipped - send the gzip as the raw body and do
# not set Content-Encoding, or the edge will decompress it and the
# upload will hang against a Content-Length that no longer fits:
{"uuid":"…","name":"Steve","stats":{"minecraft:custom":{"minecraft:play_time":…}}}
{"uuid":"…","name":"Alex","stats":{…}}

One JSON object per line, exactly the contents of each <uuid>.json plus the name from usercache.json. Line-oriented because a single {"players":{…}} document for a big server does not fit in a Worker's memory - see the shell client for a 40-line reference implementation. The response is 201 with a snapshot_id; poll GET /v1/snapshots/:id with the same key, or ask /v1/host/servers/:ref later.

How often to send it

Minecraft's counters are cumulative and never reset, so the cadence decides what the finished page is about - not how fresh it is. All three of these are supported, and the customer is the one who should pick.

Once

A complete Wrapped covering everything since the world was created. Exact, just not a single year.

Twice enough

One when you switch it on, one in December. That is the entire requirement for a year in review.

Monthly

The same page as twice, plus it stays current all year and a broken key surfaces in February instead of in December.

A year window is latest minus baseline: the customer nominates one earlier upload in their panel and everything before it drops out of the totals. Two uploads is the minimum that makes that possible, and a schedule is only a convenient way of guaranteeing the earlier one exists. A twelfth upload buys nothing a second one did not.

The early upload cannot be added later A baseline has to have been taken at the time. If the first upload a server ever sends is in December, its page is "since the world was created" for good - there is nothing earlier to subtract. Send one the day you enable it, whatever cadence follows.

Customers who would rather not send on a schedule

Some will ask, and the answer is twice a year - offered plainly, not as a downgrade. January and December produce a byte-for-byte equivalent Wrapped to a monthly cron. What monthly adds is a record of when players were active across twelve points in the year; once-and-once does not have that shape, and for someone uneasy about it that is a reasonable thing to decline.

Worth telling them alongside it: the client only ever opens the stats folder and usercache.json, --dry-run reads everything and sends nothing so they can inspect the exact payload first, and nothing is public until they publish. If your panel exposes a cadence setting, make twice a year one of the options rather than something they have to ask support for.

Claim links

A server you create is held under your partner account until somebody claims it. The claim_url from the create call hands it to whichever Discord account opens it: they sign in once and the server appears in their own panel, with nothing to paste.

Once a customer has claimed a server:

  • your key keeps working, so your scheduled uploads carry on untouched
  • they can rename it, unpublish it, upload their own icon and set a year window
  • you can no longer rename, unpublish or delete it - their page, their call
  • they can revoke your key from their panel, which is the point of it being revocable

Links are single use and last 90 days. Show it as a button - "Manage my Wrapped" - rather than printing the URL.

Panel recipes

Pterodactyl · scheduled task

The customer-facing half is a schedule on their own server, so it runs with their permissions and shows up in their activity log:

Schedule → Wrapped upload, monthly - or twice a year, if that is what the customer picked (how often to send). Task → Send command does not work here (this is a shell command, not a game command), so use a Backup-style task only if your build has shell tasks enabled. On a standard install, run it from your own daemon instead:

docker exec <container> sh -c \
  'cd /home/container && curl -sL https://wrapped.gg/u | sh -s -- \
     --key wgg_live_… --source pterodactyl --quiet'

Or, if you would rather not touch containers, add it to the egg's startup as a one-shot on first boot. The client is idempotent: sending the same stats twice is deduplicated on our side and costs nothing.

If the customer does not want a standing schedule, the same docker exec line run from a button - once now, once in December - is the whole thing. Nothing about the page is worse for it.

Wiring the button: add "Enable Wrapped" to your panel's server view. On click, call POST /v1/host/servers with external_id set to the Pterodactyl server UUID, store the returned key in your own database (not in an egg variable - customers can read those), create the schedule, then show the customer their url and claim_url.

Multicraft · scripts.conf + scheduled task

A Multicraft scheduled task cannot run a shell command. It runs a Multicraft command, and the one command that reaches a shell is builtin:script, which runs a script you registered in scripts.conf. Customers cannot add scripts or edit that file, which is the part that suits this well: the upload key never has to sit anywhere a customer can read it.

Four pieces, done once per node. Enrolling a customer after that is one file and one task - no config edit, no daemon restart.

1 · the script, in the Multicraft base directory (the one holding multicraft.log). Not in a server directory - a script under {SERVER_DIR} is one the customer can rewrite over FTP:

# {BASE_DIR}/wrapped.sh - owned by the Multicraft user, chmod 750
#!/bin/sh
set -eu

# Multicraft exports every scripts.conf placeholder as an environment variable.
KEYFILE="$BASE_DIR/wrapped-keys/$SERVER_ID"
[ -f "$KEYFILE" ] || exit 0     # not enrolled - nothing to do, quietly

# In the environment, not in --key: argv is readable in /proc by every
# other user on the box.
WRAPPED_KEY=$(cat "$KEYFILE"); export WRAPPED_KEY

cd "$SERVER_DIR"
curl -sL https://wrapped.gg/u | sh -s -- --source multicraft --quiet

Starting from $SERVER_DIR is all the client needs: it reads level-name from server.properties, finds the stats folder on 26.X and older layouts alike, and picks up usercache.json and server-icon.png sitting next to it. On the node it needs curl, python3 and outbound HTTPS, and nothing else - it never speaks to the running server.

If you would rather not fetch a script on every run, save the client once with curl -sL https://wrapped.gg/u -o {BASE_DIR}/wrapped-upload.sh and end the script with sh "$BASE_DIR/wrapped-upload.sh" --source multicraft --quiet instead. It is POSIX sh with no dependencies of its own.

2 · register it in scripts.conf, which sits in the base directory unless multicraft.conf points somewhere else:

[wrapped]
servers=all
command={BASE_DIR}/wrapped.sh

servers=all is fine here: the script exits without doing anything for a server that has no key file, so this stays a one-time edit however many customers enable it.

3 · the command, under Advanced → Commands. Leave Chat empty so no player can set it off in game, set Run to builtin:script wrapped, and put the required role at the highest you have.

4 · the task, under Advanced → Scheduled Tasks. Name it Wrapped upload, pick that command from the dropdown, set the interval monthly - or twice a year, if that is what the customer picked (how often to send) - and set it to run whether or not players are online. The game server does not need to be running either, because builtin:script is executed by the daemon rather than sent into the console; the daemon does have to be up at the time, the same caveat Multicraft notes for its setup script.

Enrolling a server is then just the key file. Call POST /v1/host/servers with external_id set to the Multicraft server id, write the returned upload_key to {BASE_DIR}/wrapped-keys/<server id> - mode 600, owned by whichever user the daemon runs scripts as, which on a Linux multiuser install is that server's own user - and create the task. A key rotation rewrites that one file; a cancellation deletes it and the script goes quiet by itself.

Using the Multicraft server id as external_id means you never have to store one of our ids at all: address the server as ext:<id> everywhere afterwards, and $SERVER_ID in the script is that same number.

The first run Give the task a start time a minute out and no interval when a customer first enables it. Multicraft runs it once, and that upload is the baseline every year window is measured against - skip it and this server can never have one. Two one-off tasks, one now and one in the last week of December, are the whole thing for a customer who would rather not leave a schedule in place.

The same script can be registered as _stopped to upload on every shutdown instead of on a schedule, but uploads are capped at 12 a day per server and a restart loop would eat that. If you go that way, stamp $BASE_DIR/wrapped-keys/$SERVER_ID.sent with date +%Y-%m after a successful run and exit early while it still matches.

Your own panel · the whole flow in pseudocode 
on customer clicks "Enable Wrapped":
  r = POST /v1/host/servers
      { name: server.name, external_id: server.id }
  db.save(server.id, r.upload_key)
  run_now(server)                 // so they see something today - and this is
                                  // the baseline. skip it and a year window is
                                  // never possible for this server again
  if customer.wants_a_schedule:   // their call, not yours
    schedule_monthly(server, "curl -sL https://wrapped.gg/u | sh -s -- " +
                             "--key " + r.upload_key + " --source myhost --quiet")
  else:
    remind(customer, "december")  // one more run is the whole difference
  show(r.url, r.claim_url)

on customer clicks "Upload now":
  run_now(server)
  poll GET /v1/host/servers/ext:{server.id} until last_snapshot.state != "queued"

on customer cancels or deletes the server:
  POST /v1/host/servers/ext:{server.id}/key   // orphan the old key
  // leave the page up unless they ask - it is their players' year

What we ask of you

  • Ask the customer first. These are their players' stats. A Wrapped should be a button they press, never something switched on for them.
  • Show them the claim link. They should be able to take the page over without going through your support queue.
  • Let them choose the cadence. Monthly is our suggestion, not a requirement - two uploads a year produce the same Wrapped. Anyone who would rather not send on a schedule should be able to say so and still have a page.
  • Keep partner tokens off game servers. One leaked token is every customer you have.
  • Do not resell it. It is free for you and free for them. Bundle it, brand your own button however you like, but do not put it behind a price.

We read the stat counters and the name that goes with each UUID. Never chat, commands, logs, IPs, coordinates, builds or inventories - the shell client only ever opens the stats folder and usercache.json, and you can read the whole thing at wrapped.gg/u before you run it.

FAQ

Does anything get installed on the game server?

No. There is no plugin, no mod and no agent. The shell client is a single script that runs, reads files the server already wrote, posts them and exits. Nothing is left behind and nothing has to keep step with Minecraft versions.

What does it cost?

Nothing, for you or your customers. There is no revenue share, no per-server fee and no paid tier to upsell. If that ever changes, servers already created keep working.

Can I white-label it?

Half of it. Your panel is yours - call the button what you like, no attribution required. The Wrapped page itself carries the customer's name and icon, not ours, but the share cards end on "make your own free at wrapped.gg", and that line stays: it is the only distribution this has.

A customer moved hosts. What happens to their page?

If they claimed it, nothing - it is theirs, the URL is unchanged, and they can keep uploading from the panel or the shell. If they never claimed it, generate a claim link and send it to them on the way out. Please do that rather than deleting it.

Modded, proxied and Bedrock servers?

All fine. It reads files, so the loader is irrelevant - Vanilla, Paper, Purpur, Fabric, Forge, NeoForge. Behind a BungeeCord or Velocity proxy, point it at each backend server's own folder; each one has its own stats. Geyser and Floodgate players are included and can search their name with or without the prefix.

Can I test without touching a real customer?

Yes - create one with an external_id like test-1 and "published": false, upload your own world's stats to it, look at the page, then DELETE it. Nothing is public until you publish, and the delete removes every upload and build with it.
